 Vento Ecosystem — Shared Architecture, Software Engineering Principles & AI Agent Rules

## 1. Ecosystem Overview
`D:\projects\vento` (`https://github.com/mehmetkurt/vento.git`) is the umbrella Git repository containing shared workspace rules, documentation, and unified release tooling alongside two independent Git Submodules that share a common offline cryptographic licensing protocol, brand identity, and engineering baseline:

1. **`ventoPOS/`** (`https://github.com/mehmetkurt/ventoPOS.git`):
   Customer-facing Android mobile POS, field pickup/delivery tracking, customer/service management, cash ledger, and HPRT HM-A300E **ESC/POS raster** thermal label printing application (legacy `CPCL` API/class names remain for compatibility).
2. **`ventoPOS_Keygen/`** (`https://github.com/mehmetkurt/ventoPOS_Keygen.git`):
   Private administrator-only Android mobile application for offline Ed25519 license generation and WhatsApp delivery.

Both subprojects are registered via `.gitmodules` in the root repository while strictly preserving their own independent Git commit histories, branches, `.gitignore` rules, and remote origins.

## 2. Language & Agent Reporting Policy (Strict)
- **Code & Developer Artifacts**: MUST be written exclusively in **English**.
  - Class names, method names, variables, file/folder names, constants, comments, documentation, rule files, and Git commit messages.
- **User Interface (UI)**: MUST be written exclusively in **Turkish**.
  - All screen titles, labels, form hints, validation messages, SnackBars, dialogs, thermal receipt/label headers, and WhatsApp share templates must use natural Turkish suitable for field operations in Türkiye.
- **AI Agent Communication & Reporting Rule**:
  - Every AI agent working in this workspace MUST follow `AGENTS.md` from start to finish and produce **all technical analyses, progress updates, modified file summaries, verification steps, and final reports to the user exclusively in Turkish**.

## 3. Shared Tech Stack, Software Engineering Principles & Code Quality Standards
- **Framework & Target**: Flutter (Android target, standalone signed APK distribution, `minSdk = 24`, `targetSdk = 36`, Java/Kotlin 17).
- **Language**: Dart with Sound Null Safety and strict static typing (`flutter_lints`).
  - Always declare explicit return types and parameter types on public APIs.
  - Avoid `dynamic` except at untyped JSON / `MethodChannel` boundaries.
- **SOLID & Clean Architecture Dependency Rule (`presentation -> domain <- data`)**:
  - The `presentation` layer MUST NEVER directly access Drift DAO classes or SQLite table definitions; it communicates strictly via `domain/repositories` contracts and Riverpod providers.
  - `lib/presentation/**` MUST NOT import `data/database/daos/**`, `database_providers.dart`, `appDatabaseProvider`, `locationsDaoProvider`, or concrete `data/repositories/drift_*` implementations; use `data/providers/presentation_safe_providers.dart` + `domain/repositories` contracts and enforce via `dart run tool/check_presentation_layer_imports.dart` plus `dart run tool/check_design_system_tokens.dart` (no `VisualDensity.compact`; use `AppTypography`).
- **State Management**: `flutter_riverpod` (`v2.x`).
  - **Zero business logic inside UI Widgets or Screens** (`StatelessWidget`, `StatefulWidget`, `ConsumerWidget`, `ConsumerStatefulWidget`).
  - Widgets and screens render state and dispatch user intents to Riverpod `StateNotifier` / `Notifier` providers.
  - **DRY (Centralized Shared Components)**:
    - Module tab bars (`VentoModuleTabBar`), scroll-reactive collapsible search/filter headers (`VentoCollapsibleFilterScaffold`), modal bottom sheet wrappers (`VentoModalSheetScaffold`), structured customer address fields (`VentoStructuredAddressFields`), tri-state elevator selectors (`VentoElevatorSelector`), template-free direct WhatsApp chat buttons (`VentoDirectWhatsappButton`), future-scheduled pickup/delivery badges (`VentoFutureScheduleChip`), warranty return badges (`VentoReturnOrderBadge`), order financial breakdown boxes (`VentoOrderFinancialBreakdownBox`), and settings navigation definitions (`SettingsNavigationRegistry` synchronizing App Drawer settings submenu items with `PrinterSettingsSheet` tabs) MUST NOT be duplicated per screen; always use the single canonical component/registry from `lib/presentation/design_system/`, `lib/presentation/navigation/`, or `lib/presentation/widgets/common/`.
- **Single-Widget-Per-File (`1 Widget = 1 .dart File`)**:
  - Every `StatelessWidget`, `StatefulWidget`, `ConsumerWidget`, or `ConsumerStatefulWidget` MUST reside in its own dedicated `.dart` file in `snake_case.dart`.
  - Private helper widget classes (`class _Foo extends StatelessWidget`) and widget-returning `_build*` methods (>20 lines) are forbidden; extract them into separate files.
  - Keep barrel `export` statements when splitting existing files so `test/unit/` imports never break.
- **Centralized M3 Design System, Contrast & SafeArea Rules**:
  - Never use hardcoded `Color(0x...)`, `Colors.slate/grey`, raw `TextStyle(fontSize: ...)`, or manual `Container(decoration: BoxDecoration(...))` for cards/chips/buttons.
  - Always use `AppColors`, `AppTypography`, `AppSpacing`, `AppRadius`, and `lib/presentation/design_system/` components.
  - **Mandatory `SafeArea` (`targetSdk = 36`)**: All full-screen `Scaffold` bottom bars (`bottomNavigationBar`) and all `showModalBottomSheet` sheets (`useSafeArea: true` + inner `SafeArea(top: false, bottom: true)` + keyboard `MediaQuery.viewInsetsOf(context).bottom`) MUST respect system navigation and keyboard insets.
  - **Blue & Filled Button Contrast Standard**: All blue-toned (`AppColors.action`, `AppColors.actionDark`, `AppColors.primary`, `AppColors.primaryDark`) and dark filled buttons (`ElevatedButton`, `FilledButton`) and selected solid choice/filter chips MUST render text and icons in pure white (`#FFFFFF` / `Colors.white`). Never apply raw `AppTypography.*` styles carrying `AppColors.textPrimary` inside filled buttons or dark/blue selected chips without overriding `color: Colors.white`.
  - **Touch Target Size**: Do not vertically compress action buttons with `VisualDensity.compact`; preserve a minimum `44dp` vertical touch target height.
  - **Mandatory Pull-to-Refresh (`RefreshIndicator` + `AlwaysScrollableScrollPhysics`) Across All Lists**: Every list screen and list tab view (`CarpetOrdersTabView`, `ServiceRequestsTabView`, `AllCustomersTabView`, `DebtorsListTabView`, `CashLedgerScreen`, `ExpensesScreen`, `OnSiteAppointmentsTabView`, `SubcontractorFactoriesScreen`, routing/distribution lists, and any new list view added in the future) MUST support downward pull-to-refresh via `VentoCollapsibleFilterScaffold(onRefresh: ...)` or `RefreshIndicator` paired with `AlwaysScrollableScrollPhysics()` so operators can always swipe down to reload live repository/SQLite state even when a list is short or empty.
- **Immutability & Domain Invariants**:
  - All domain entities, models, and state classes must be `@immutable` with `final` fields and deterministic `copyWith` implementations.
  - **Service Request -> Order Conversion Rule**: Whenever a `ServiceRequest` is converted into a `CarpetOrder` (manually or via routing), the new order's initial status MUST unconditionally be `CarpetOrderStatus.received` (`Teslim Alındı`); opening the edit screen must never auto-advance the status to `Yıkamada`.
  - **All-Accounts Device Address Book & Live Contact Synchronization Rule**: Address book searches and contact cache synchronization MUST NOT be restricted to `com.google` accounts; they MUST scan all active (`DELETED = 0`) device contact sources (Phone/Device local storage `null`, SIM, OEM accounts, and Google) without loading photos (`CursorWindowAllocationException` prevention) and automatically revalidate when the app resumes (`AppLifecycleState.resumed`), when customer/request picker screens open, or when the native contacts database changes.
  - **Atomic Receipt Sequence & Immutability**: Order/receipt numbers (`receiptNo` / `receipt_number`) MUST be allocated atomically inside the same SQLite transaction as order persistence via `ReceiptSequences`, enforced by a database-level `UNIQUE` index on `carpet_orders.receipt_number` (protecting active, cancelled, and soft-deleted historical records from reuse), rendered strictly `readOnly: true` (locked) on `CarpetOrderFormScreen`, and kept strictly immutable whenever an existing order is edited.

## 5. Shared Ed25519 Offline Licensing Contract (`ventoPOS` <-> `ventoPOS_Keygen`)
Any modification to device code derivation or activation token verification MUST keep `ventoPOS` (`LicenseConstants` / `LicenseCodec`) and `ventoPOS_Keygen` (`KeygenConstants` / `Ed25519LicenseSigner`) 100% byte-for-byte compatible:

- **Device Code Format**: `VP-XXXX-XXXX-XXXX-XXXX`
  - Derived from native hardware identifiers hashed with `VENTOPOS-HW-V1|` -> first 9 bytes + 1-byte SHA-256 checksum over `['V', 'P', ...fingerprintBytes]`, encoded in unambiguous 32-char Base32 (`ABCDEFGHJKLMNPQRSTUVWXYZ23456789`).
- **Activation Token Format**: `VPK1-<base64UrlUnpadded(67 bytes)>`
  - Binary payload: `[protocolVersion (1B = 1), expiryDayOffsetHigh (1B), expiryDayOffsetLow (1B), ed25519Signature (64B)]`.
  - Canonical signed message (26 bytes): `utf8("VP-LICENSE-V1:") + [version (1B)] + fingerprintBytes (9B) + [expiryHi, expiryLo]`, where `expiryDayOffset == 0` denotes a lifetime license and `> 0` denotes days after `2026-01-01T00:00:00Z`.
- **Key Separation**:
  - `ventoPOS` embeds **ONLY** the 32-byte Ed25519 Public Verification Key.
  - **NEVER** copy, embed, or log the Ed25519 Private Signing Seed inside `ventoPOS`.
